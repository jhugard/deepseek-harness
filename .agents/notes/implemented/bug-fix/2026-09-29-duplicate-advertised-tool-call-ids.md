# Agent Note: A repeated advertised tool-call id is a separate occurrence

Status: implemented

English | [中文](2026-09-29-duplicate-advertised-tool-call-ids.zh.md)

## Problem

Local OpenAI-compatible servers (e.g. llama.cpp serving the OpenAI **Responses** API) emit several output items carrying the **same `call_id` and the same `id`** for the parallel tool calls of one response. The pi-ai Responses adapter composes the harness tool-call id as `` `${call_id}|${id}` `` and tracks its slots by `output_index` only, with no id dedup — so N parallel calls compose N byte-identical harness ids of the shape `call_<tok>|fc_<tok>`. Five independent surfaces presupposed id uniqueness:

1. The v4 reload path — `SessionLogScanner.finish()` runs `assertReleasedV4Relationships` unconditionally and hard-refuses at the first duplicated id, so a *current-generation* session is permanently unreadable and unresumable: `SessionFormatError: assistant/message repeats advertised tool call call_<tok>|fc_<tok>`.
2. The stored migration — the v0→v1, v1→v2, and v3→v4 relationship walkers carry the same released-relationship assertion, so migrating any historical log containing a duplicated id is refused with `SessionFormatUnsupportedMigrationError`.
3. The Web UI — the `ConversationNodeAssembler` holds one Context per id, so every `tool/call` and `tool/result` match for a repeated id re-attaches to that single Context: N parallel calls and their N results render as one card, and the user sees fewer calls than ran.
4. The recovery writer — `ToolCallRecovery` keyed its pending map by id, so a step advertising one id twice recorded one pending entry and `results()` emitted one synthetic closer where the reader required one per occurrence. Interrupting such a step wrote a log the relaxed reader then refused: `SessionFormatError: step/end leaves unresolved tool call call_<tok>|fc_<tok>`. A reader relaxed to occurrences and a writer still keyed by id produce logs their own format gate rejects.
5. The Trajectory ledger — `deriveTrajectoryLayout` indexed results, start times, and advertised ids by `callId`, and the row identity `trajectoryRecordId` resolves to `tool\0call\0<callId>` for a cell carrying a `callId`. Every occurrence of a repeated id therefore read the same result list and the same start time, and two rows carried the same identity, which is the React key, the `data-trajectory-row-key`, the search-index key, and the selection key. Measured on a two-call fixture: both rows showed the second call's result preview, start time, and duration, and the rendered table logged `Encountered two children with the same key` twice — the repeated rows and blank rows reported in the discussion.
6. Cross-view Inspect — a Chat card's Inspect action addressed the target view with the bare id, and the Trajectory ledger resolved it with `find`, so Inspect on the second of two same-id cards opened the first occurrence's record.

## Decision

Treat the advertised id as an occurrence key rather than a unique identity.

In the session format walkers, advertised tool-call lifecycles are tracked as **occurrence lists** and `tool/call` / `tool/result` references resolve in stream order:

- v0→v1 relationships admit a duplicate advertisement under the new `allowDuplicateAdvertisedToolCall` extension (bare v1 stays strict). The flag is part of `RELEASED_V2_RELATIONSHIP_EXTENSIONS`, so released v2 artifacts restore with it unconditionally, and v1→v2 hard-enables it in the released v2 relationship extensions.
- v3→v4 relationships admit duplicated ids unconditionally (there is no extension mechanism at that seam).

Truly indistinguishable cases — a repeated start for the same id, a changed name or arguments, a dangling result — are still refused.

In the client, the assembler tracks one `OccurrenceRef` per base key and routes each accepted Match to an occurrence: occurrence 0 keeps the bare base key, so the common single-occurrence case stays byte-identical. Two optional `ConversationNodeDefinition` hooks let a Definition opt in without changing any other Definition: `settle(match)` marks the current occurrence terminal so a later same-id Match opens a fresh one, and `dedupe(match)` returns an already-seen per-occurrence identity to drop a re-emission (publication `none`) — e.g. a prune pass re-sending a `tool/result` whose `message.id` was already applied. The chat and trajectory tool Definitions register both hooks.

In the recovery writer, `ToolCallRecovery` maps each id to its **occurrences in advertisement order** (`PendingCall` list). `observe()` pushes one entry per advertised `tool-call` block; `tool/call` marks the first unstarted occurrence; an appended `tool/result` answers the first started occurrence in its own turn and step, else the first unstarted one, and removes only that occurrence. `results()` emits one synthetic result per remaining occurrence. A single-occurrence id keeps its previous output byte-for-byte: same message ids, same `sourceEventSeqs` presence, same timestamps and sequence base.

In the Trajectory layout, one pass-scoped `OccurrencePairing` counts advertised blocks, orphan results, and sub-dispatch records separately, so the Nth block of an id pairs with the Nth result of that id in stream order — the same pairing the conversation assembler applies. Each tool cell carries an explicit `recordId` from `toolRecordId(kind, callId, occurrence)`, and occurrence 0 resolves to the identity `trajectoryRecordId` already derived from the bare `callId`, so single-occurrence rows keep their identity byte-for-byte while later occurrences append `\0<N>`. `indexResults` returns the result list per id, `callStartById` and `callById` hold one entry per occurrence, and the running-call placeholders are laid only for occurrences beyond the durable advertisements. Each assistant message source block carries the occurrence of its call, and `openCallSummary(callId, occurrence)` opens the Nth ledger tool record of that id, so a jump from a message's Block list lands on the tool row of the clicked call rather than always the first one. Because `appendTrajectoryPartialLayout` re-derives the in-flight step from scratch, `TrajectoryView` passes the counts the finalized layout consumed (`advertisedToolCallCounts`, which excludes the partial's own turn and step), so a streamed call reopens the occurrence the finalized layout gave it instead of opening a second one.

For Inspect, the assembler publishes `occurrence` on every `ConversationNodeContext`, the chat Tool Definition copies it into `ToolChatData`, and `ToolCallTree` passes it to `inspectCall(callId, occurrence)`. `ConversationViewDefinition.toolCallFocus(callId, occurrence)` encodes the pair with `occurrenceKey` — occurrence 0 is the bare id, so a focus persisted before this change still resolves — and `TrajectoryView` decodes it with `parseOccurrenceKey` before handing both parts to the ledger, which selects the Nth tool record of that id. An occurrence no longer advertised (trimmed by a fork) clamps to the last record still present.

## Alternatives considered

**Keep refusing duplicates and fix the provider.** Rejected: the id comes from the provider's wire format, and no released writer ever guaranteed the uniqueness the guards presuppose; already-stored sessions stay unreadable, and the provider class is common in local deployments. Measured confirmation: one live log carries 201 duplicate-id advertisements across 22 turns, so a provider-side fix cannot make any already-stored session readable.

**Repair a corrupt tail at resume instead of fixing the writer.** Rejected: `interruptedTurnClosers` finds nothing to close in such a log — the interrupted turn was already committed with its (too few) closers, so the imbalance is in the durable prefix, not in an open tail. Making the stored log readable requires inserting the missing occurrence closer and renumbering every later event, which is a new generation rather than a repair, and the adjacent-migration rule forbids rewriting a committed generation in place.

**Make the id unique at the pi-ai seam (append the `output_index`).** Rejected: it changes the harness id format for every provider — stored sessions, replay lookups, and the wire vocabulary all break — where keeping the bare id for the single-occurrence case byte-identical is exactly what occurrence 0 preserves.

**Key the assembler by a call/result pair instead of the id.** Rejected: results reference their call by id, so the id must remain the join key; the fix is to give the key multiplicity (occurrences) while keeping the join.

## Consequences

A session with duplicated advertised ids is readable and resumable — the v4 reload admits it and historical logs migrate — the Web UI renders each occurrence as its own card, pairing each result with its call in stream order, the Trajectory ledger gives each occurrence its own result, start time, duration, and row identity, Inspect opens the record of the card it was clicked on, and an interrupted step closes every occurrence it advertised, so the writer no longer produces logs its own reader refuses. Single-occurrence sessions are byte-identical: occurrence 0 keeps the bare base key, bare v1 artifacts stay strict, single-occurrence closers are unchanged, single-occurrence Trajectory rows keep the identity they had before, and an Inspect focus for a single-occurrence id stays the bare call id. The strictness that catches real corruption (repeated start, changed name or arguments, dangling result) is retained.

A log written before the writer fix is not repairable by resume: its imbalance is inside a committed turn, and admitting it would mean rewriting a released generation. Such a session stays unreadable.

## Testing

`packages/session/session-format-v0-to-v1/tests/relationships.spec.ts` pins the extension-gated admission: bare v1 stays strict, extended v1 admits a duplicate advertisement and resolves references in stream order, and repeated start, changed arguments, and a dangling result are refused. `packages/session/session-format-v1-to-v2/tests/validation.spec.ts` pins the hard-enable in the released v2 extensions. `packages/session/session-format-v3-to-v4/tests/relationships.spec.ts` pins unconditional admission at that seam, and its cross-boundary test replays a duplicate advertisement through `ToolCallRecovery` and reopens both closer sets: the one-closer-per-id set is refused with `step/end leaves unresolved tool call`, the per-occurrence set is accepted. `packages/client/ui-conversation/tests/conversation-assembler.client.spec.ts` pins occurrence splitting: C,R,C,R and C,C,R,R pair each result with its own call, a prune re-emission is dropped, and a per-call delta re-affirms the live occurrence instead of opening a fresh one. `packages/core/session/tests/repair.spec.ts` pins the writer: an id advertised twice in one step closes both occurrences, a started and an unstarted occurrence get their own codes, and a result answering one of two leaves only the other to close. `packages/client/ui-trajectory/tests/layout.client.spec.tsx` pins the ledger: one message advertising two calls under one id yields two rows with their own tool name, preview, result preview, start time, and duration; a single-occurrence id keeps the identity `trajectoryRecordId` derives from the bare call id; the orphan result of a repeated id becomes its own record instead of being dropped; and `table.client.spec.tsx` opens the second of two same-id call blocks and asserts the selected ledger row is the second tool record. The Inspect seam is pinned at each hop: `conversation-assembler.client.spec.ts` publishes the occurrence index on the Context handed to the Definition, `ui-tool/tests/tool-call-tree.client.spec.tsx` forwards the node's occurrence to `inspectCall`, `conversation-definitions.client.spec.ts` encodes it into the focus key, and `table.client.spec.tsx` opens the record named by an occurrence-keyed inspect request.
